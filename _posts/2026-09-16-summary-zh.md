### [HTTP 新标准方法 QUERY：带正文的安全、可缓存读请求](https://www.infoq.cn/article/BmJh0DzGPYBEl1zlyO0C) ⭐️ 8.0/10

IETF 于 2026 年 6 月发布 RFC 10008，为 HTTP 引入新的 QUERY 方法，这是继 2010 年 PATCH 之后的首个新标准 HTTP 动词，由 Julian Reschke、James Snell 与 Mike Bishop 编写，起源于 Asbjørn Ulsberg 在 2019 年 HTTP Workshop 上重提的讨论。QUERY 可像 POST 一样在请求正文中发送过滤条件，同时保留读取操作的安全、幂等与可缓存语义；只要缓存键包含请求内容，响应即可被缓存，服务器还能通过新的 Accept-Query 字段声明支持该方法。它补上了 GET（过滤条件受 URL 长度限制、易泄露到日志且难表达嵌套结构）与 POST（不安全、不幂等，缓存会跳过）之间的第三种选择，并被规范定位为两者的可选用补充而非替代。GraphQL、Elasticsearch 这类已用 POST 正文传输复杂读取请求的场景从此有了基于标准的方案；Rust 的 http crate 已合并相关支持，.NET、Axum、Quarkus 与 Bruno 也在跟踪跟进。与 PATCH 类似，QUERY 的实际普及预计需要以年为单位衡量。

rss · InfoQ 推荐 · 9月15日 05:00

**「背景」** HTTP 是 Web 运行所依赖的请求与响应协议，其规范由 IETF 的 HTTP 工作组（httpbis）制定，再由 RFC Editor 以 RFC 形式发布。新方法极为罕见，因为每种方法都必须被客户端、服务器、代理和缓存一致理解并支持，才能在实践中可靠使用。QUERY 正是为弥补 GET 无法携带复杂正文、POST 又缺乏安全与幂等语义的空白而设计，提供了第三种选择。

**「影响」** 对 API 设计者及 GraphQL、Elasticsearch 这类检索服务而言，QUERY 提供了标准化的带正文读取方式，复杂查询不再受 URL 长度与日志泄露限制，客户端也能安全重试。鉴于规范明确将其定位为可选补充且工具生态仍在跟进，实际部署收益将随着框架与服务器支持逐步显现。

**「社区讨论」** 在 r/webdev 与 Hacker News 的讨论中，不少开发者质疑“这不就是 GET 吗”，但也有观点认为带正文的 GET 只是变通手段且容易静默失败，明确的新方法能确保对端真正支持请求正文。讨论还指出，Cloudflare 曾以伪造 GET 缓存键的方式非官方缓存 POST 响应，这正是缺少 QUERY 这类方法时各方不得不采用的绕行方案。

Google 在官方博客发布了 Gemini 3.8 Live 和 Gemini 3.8 Live Extended Thinking 两个新版本，涉及语音交互与推理能力的改进。社区早期反馈显示，有用户能在 Workspace 账号下使用该模型，并提到延迟较低、语音自然且能应对重度口音。一位用户用它进行南非荷兰语的实时对话和语法练习，称效果出色。但也有用户指出，Google AI Plus 用户尚未获得该版本更新。

**「为何值得关注」** 这是来自官方渠道的模型更新公告，且社区首批体验反馈整体正面，因此短期内值得留意。需要明确的是，改进的实际效果目前主要依赖用户初步体验，尚未经过大范围测试或长期验证。

**「内容切入角度」** 可做角度：从社区首批体验入手，整理 Gemini 3.8 Live 在语音交互实际使用中的表现，突出 Workspace 账号可用性、低延迟与多语言（如南非荷兰语）场景。不进行性能对比或结论预测。

**「社区反馈」** 多数评论者给出正面体验：支持 Workspace 账号、语音自然、延迟低，还有人称赞其生成文本的可读性。分歧方面，有用户认为 Google 没有同步向 AI Plus 用户推送该版本令人失望，也有评论对 Gemini 相对其他产品的竞争位置持观望态度。

### [Typesafe AI 发布 System One 与 Jev：主打快速类型化推理](https://typesafe.ai/blog/introducing-system-one-models-and-jev) ⭐️ 7.0/10

Typesafe AI 发布了 System One 系列模型和配套的 Jev，定位是快速类型化推理（fast typed inference）而非通用文本生成。根据社区对文档的转述，Jev 的输入是结构化状态与问题（问题类型包括 Choice、Score 等），输出对应答案、概率和置信度。社区讨论指出，它与能输出图灵完备语言代码的通用生成模型定位不同，因此双方的速度对比是否公平仍有争议。现阶段受影响的主要是关注结构化分类、评分等场景的开发者，具体性能数值与基准在材料中并未给出。

hackernews · albelfio · 9月15日 19:25 · [社区讨论](https://news.ycombinator.com/item?id=49717558)

**「为何当下值得注意」** 这次发布把&quot;结构化推理与通用生成&quot;之间的成本与速度取舍摆到台前，引来开发者对模型适用边界的讨论；但 Jev 的实际性能与局限目前只停留在社区观点层面，尚未见可验证的基准数据支撑。

**「可做角度」** 可做角度：梳理 Jev 的输入输出设计，说明它如何用&quot;类型化推理&quot;换取生成能力，并对比它和通用生成模型在分类、评分等场景下的适用边界；同时如实反映社区对速度对比的质疑，而不是把宣传语直接写成结论。

**「社区讨论要点」** 社区大体认可这是一个&quot;有真东西、方向新&quot;的发布，但分歧也很明显：有人质疑与生成模型比速度的说法有误导性——Jev 只能产出结构化输出，而通用生成模型理论上能完成任何计算；也有人结合实际体验，讨论把它与&quot;契约式设计&quot;（design-by-contract）模式结合的价值。以上均为评论者个人观点，不宜当作定论。
